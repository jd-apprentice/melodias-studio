# 0003 · NES chiptune composer and cover agent

Status: proposed. The cover half exists as an experimental `melodias chip` command; the composer, the evaluator loop and the knowledge base do not.

Date: 2026-11-21

Depends on: [0002](0002-deterministic-scoring.md)

## Summary

Add an optional NES composer to `melodias-studio`, built on FamiStudio and on the offline stack the repository already uses. It has two modes:

- **Cover**: an existing track becomes an NES arrangement. Download or read the audio, separate stems with Demucs, transcribe melody and bass with Basic Pitch, map the result to the 2A03 channels, render with FamiStudio and mix a stereo master.
- **Compose**: a prompt becomes an original NES piece. The LLM writes a typed composition, never a FamiStudio file directly; a validator checks the hardware rules before the builder writes the project.

Both modes share a typed composition model, a FamiStudio adapter, a deterministic evaluator and a bounded iteration loop. The default YouTube pipeline is untouched: this is an opt-in subcommand, not a stage.

Phase 1 is cover mode, because it is already prototyped behind `melodias chip` and it proves the full cycle of source, project, render and evaluation. Compose mode comes after the model and the validator are stable.

## Motivation

The channel is 8-bit, but the current track is generated by ACE-Step from a reference window. It can sound chiptune, yet it is not constrained by the 2A03: any polyphony, any timbre, any effect. A real NES arrangement is a different product, and the reference covers that motivated this work show a clear quality ceiling that a text prompt alone does not reach.

The `melodias chip` prototype already does the mechanical part end to end: yt-dlp, Demucs, Basic Pitch, a FamiStudio text project with section textures, arpeggios, vibrato, portamento, DPCM drums, a stereo stem mix and a master. On a real battle theme it reaches a chroma correlation of 0.637 with the source, a spectral balance within one point of the reference cover and a stereo width of 0.41. What it lacks is structure: there is no typed model, no hardware validation, no report, no iteration and no compose mode.

The original proposal for this RFC described a separate `nes-composer` service built with Rig, Tokio, Axum, Qdrant, Swiftide and MCP. The goals are right. The stack is premature here: this repository is a synchronous single binary with an LLM client, a deterministic score, a SQLite history and a FamiStudio-capable prototype. Phase 1 should reuse that, not duplicate it. A service and a knowledge base only make sense after the musical loop works.

## Goals

- A typed composition model that a human, a mapper or an LLM can produce without writing project text.
- Hardware rules for the NES APU enforced in code, with tests, not only in a system prompt.
- A FamiStudio adapter that validates the project, renders it with a pinned version and verifies the WAV.
- A deterministic evaluator that separates technical validity from musical quality and states what it did not measure.
- Cover mode from a URL or a local file, with the existing Demucs and Basic Pitch tools.
- Compose mode from a prompt, starting with short original loops.
- A bounded iteration loop that turns findings into concrete changes and keeps every attempt.
- Reproducible artifacts: editable project, audio, metadata and validation report.
- Clear licensing records for examples, samples and references.

## Non-goals

- A separate repository, async runtime, HTTP API, vector database, RAG pipeline or MCP server in phase 1.
- A multi-agent deployment. One orchestrator with typed tools is enough until the loop proves itself.
- Replacing FamiStudio's engine, writing a new NES emulator or a new synthesizer.
- Exact note-for-note recreation claims. A cover is approximate unless a reference transcription is compared, and the report must say so.
- Integrating covers into the channel pipeline or the video stage. This RFC is audio only.
- Training models or redistributing copyrighted NSF, ROM, project or audio files.
- Expansion audio (VRC6, FDS, N163, S5B, VRC7) as part of "authentic NES". It can be a later profile.

## Fit with the repository

The work lives in a new `src/chip/` module family and two subcommands:

```text
melodias chip <url|file>        cover mode, experimental today
melodias compose "<prompt>"     compose mode, phase 2
```

Proposed modules:

| Module | Responsibility |
| --- | --- |
| `chip/model.rs` | Typed composition, instruments, patterns, events, hardware profile |
| `chip/validate.rs` | Hardware and structure validation, actionable findings |
| `chip/famistudio.rs` | Text project builder, CLI wrapper, render verification |
| `chip/cover.rs` | Source to stems to transcription to composition |
| `chip/compose.rs` | Prompt and LLM to composition |
| `chip/evaluate.rs` | Technical and musical checks, reference comparison, report |
| `chip/agent.rs` | Bounded loop, iteration bookkeeping |

The existing pieces are reused: `clients` for the LLM, `score` and `ffmpeg` for technical audio metrics, `history` for optional run records, `media` for yt-dlp and ffprobe. The command stays synchronous. A timeout watchdog around `Command` is enough; no Tokio is introduced for phase 1.

The external tools stay external and user-local:

- Demucs and Basic Pitch in `~/.local/share/melodias-studio/venvs/chip`.
- FamiStudio 4.5.4 and a .NET 8 runtime in `~/.local/share/melodias-studio/tools`.
- Paths overridable with `CHIP_VENV`, `FAMISTUDIO_BIN` and `DOTNET_ROOT`.

## Hardware model

A `HardwareProfile` describes the target. The first profile is `nes-2a03-ntsc`:

| Channel | Capability | Rules |
| --- | --- | --- |
| Pulse 1, pulse 2 | Duty 12.5, 25, 50 or 75 percent, 4-bit volume, sweep | One note at a time, no volume on the triangle |
| Triangle | Fixed waveform, no volume control | One note at a time, low register |
| Noise | 16 periods, short and long mode | Used for percussion, not pitched melody |
| DPCM | One sample at a time, shared channel | Percussion or speech, never overlapping |

The model also carries the pulse frequency range, the noise period table, NTSC versus PAL timing and the note range that the adapter can serialize. Values are tested against the NESdev documentation; the RFC does not hardcode a table in prose that the code does not share.

Validation rules, at minimum:

- A channel has at most one sounding note at a tick.
- Every note is inside the channel range for the profile.
- Pattern length, order and loop point are consistent.
- Every event references an existing instrument that the channel supports.
- A DPCM sample is mapped and never overlaps another DPCM event.
- Total duration, section count and pattern count stay inside configured limits.
- Chords are represented as arpeggios or split across channels, not as free polyphony.

The rules are enforced by the builder and by a `validate` step that returns findings with a code, a message and the offending event. A project that fails validation is never rendered.

## Typed composition model

The contract between the composer, the cover mapper and the FamiStudio builder is a Rust struct serialized to JSON:

```text
Composition
  title, author, system, tempo, meter, tuning
  sections[]        name, start_tick, texture, energy
  instruments[]     name, channel_kind, volume, duty, pitch, arpeggio envelopes
  patterns[]        length_ticks, channel -> events[]
  events[]          channel, instrument, note, start_tick, duration_ticks, volume, effect
  order[]           pattern index per song slot
```

The LLM or the mapper produces this model. It never writes FamiStudio text or binary files directly. The builder is the only writer, and it re-validates the model before writing.

The model is deliberately smaller than FamiStudio: it covers notes, instruments, envelopes and the effects used by the first two phases. Anything the model cannot express is out of scope until the model grows.

## FamiStudio adapter

FamiStudio is the renderer and the editable target. The adapter:

1. Checks the executable and records its version.
2. Rejects a version outside the pinned range instead of guessing flags.
3. Builds the text project from the composition model.
4. Validates the project through the model and, when available, by asking FamiStudio to render it.
5. Runs the CLI with fixed arguments and a timeout.
6. Checks the exit code and that the WAV exists and is readable.
7. Returns the paths and the render metadata.

The text format is used because it is diffable, reviewable and easy to generate; the binary `.fms` can be produced by FamiStudio later. The adapter pins 4.5.4 for now. A version bump is a deliberate change with a render test, not an implicit one.

Why FamiStudio and not the alternatives:

- `chipcore` (the current Rust prototype) is MIT and small, but its engine and instrument model are thinner, and it does not give an editable project or NSF/ROM export.
- `audio8bit` is PolyForm Noncommercial and would be a dependency for a noncommercial tool; its arrangement ideas are reimplemented, its code is not copied.
- `ChipForge` has an MIT core and a good tracker, but composing and converting are GUI-only and its project format is not a stable CLI contract.
- Furnace and the classic trackers do not offer a headless convert-and-render path.

## Cover mode

Cover mode is the current prototype, formalized:

1. Resolve the source: download the audio with yt-dlp or read a local file, normalize to 48 kHz stereo PCM.
2. Separate drums, bass, other and vocals with Demucs.
3. Transcribe the other and bass stems with Basic Pitch.
4. Analyze the drums stem: onsets, then low, mid and high band energy to classify kick, snare and hat.
5. Detect tempo and key. Key snapping is optional and off by default: on a real track it lowered the chroma correlation from 0.70 to 0.45.
6. Build the composition: melody on pulse 1, harmony or arpeggio on pulse 2, bass on the triangle, kick and snare on DPCM, hats on noise.
7. Assign a texture per section from the source energy: sparse keeps melody and bass, normal adds harmony and drums, full adds arpeggios, hats and vibrato.
8. Write the project, render, export stems, mix stereo, master to -16 LUFS.
9. Evaluate and report. Iterate only when a finding is actionable and the budget allows.

The prototype already does steps 1 to 8. The RFC adds the model, the validation, the report and the bounded iteration.

## Compose mode

Compose mode starts after the model is stable:

1. The prompt is interpreted by the existing LLM client, with the hardware profile and a JSON schema in the request.
2. The model is validated. Invalid output is returned to the model with the findings, at most twice.
3. The builder writes the project and renders it.
4. The evaluator scores it. The loop may ask for a revision.
5. The first target is an 8 to 16 bar loop with a clear form; full pieces come later.

The LLM never runs shell commands. It calls typed tools through the orchestrator, and every tool validates its own arguments.

## Evaluation

Evaluation has two layers, and the report always says which metrics were measured.

Technical gates, hard failures:

- The WAV exists, decodes and has the expected sample rate and channel count.
- Duration is inside the requested range.
- No accidental silence and no clipping beyond the configured ceiling.
- Integrated loudness and true peak are inside the master targets.
- The render did not leave the project in an invalid state.

Musical checks, warnings or scores:

- Channels used, notes per channel and polyphony per tick.
- Note range and duty usage per channel.
- Note density and onset rate per section.
- Section contrast: texture, energy and channel count.
- Melody, bass and percussion presence.
- Tempo and key estimates, when the tools can measure them.
- Reference comparison when a transcription exists: aligned chroma, onset agreement, tempo difference and note overlap. Spectra alone are not evidence of a faithful recreation.

The report is JSON:

```text
status: passed | warning | failed
measured: metrics with value, unit and threshold
unmeasured: metrics with the reason
findings: code, severity, message, event reference
reference: comparison summary or null
limitations: what the evaluation cannot conclude
```

## Iteration loop

The loop is bounded and auditable:

- Default budget: 2 rounds per artifact, configurable and capped.
- A round starts from the worst actionable finding and applies one change to the composition or the mapping.
- Every round keeps its project, render and report.
- The loop stops on acceptance, on an empty finding set, or on the budget.

Acceptance for phase 1:

- All technical gates pass.
- The project validates against the hardware profile.
- The report states the musical checks and the limitations.
- A cover does not claim fidelity unless the reference comparison ran.

## Artifacts

```text
output/chip/<slug>/          cover
output/compose/<slug>/       compose
  project.txt                editable FamiStudio project
  audio.wav                  stereo master
  audio.mp3                  192 kbps
  preview.mp3                25 s excerpt, when the track is long enough
  report.json                validation and evaluation
  meta.json                  source, tools, versions, settings
  references.json            optional, licensing and provenance
  work/                      stems and intermediate files, removed unless --keep-work
```

## Security

- No arbitrary shell from the model. Only typed tool calls.
- Paths are restricted to the command output directory and the configured tool paths.
- Every external process has a timeout, a size limit and an output check.
- Existing projects are never overwritten silently; each run gets its own directory.
- Arguments, versions, durations and errors are logged.
- Untrusted file names and metadata are sanitized before they reach a path or a project field.

## Licensing

- Examples and datasets must be own, CC0 or explicitly compatible. Every entry records origin, license and allowed uses.
- Covers of commercial tracks are derivative works. They stay personal and are not published without permission; the report records the source.
- No redistribution of copyrighted NSF, ROM, project or audio files.
- The tools keep their own licenses: FamiStudio MIT, Demucs MIT, Basic Pitch Apache 2.0, FamiStudio CLI as distributed by its project.

## Phases

### Phase 1: cover vertical slice

- Formalize `melodias chip` on the typed model.
- Implement the hardware profile, the validator and the FamiStudio adapter.
- Implement the technical report and the musical checks that do not need new dependencies.
- Keep the existing texture, DPCM and stereo mix.
- Tests: model round trip, validator rules, project builder, report schema.
- Acceptance: a cover of a real track produces a valid project, a WAV, a report with measured and unmeasured metrics, and no manual step after the source is provided.

### Phase 2: compose mode

- Implement the LLM to model call with a schema and hardware rules.
- Support 8 to 16 bar loops with intro, A and B sections.
- Reuse the validator and the builder; no new renderer.
- Acceptance: a prompt produces a valid project, a render and a report, with at least one revision round exercised in tests.

### Phase 3: evaluation and iteration

- Add reference comparison for covers.
- Turn findings into concrete composition changes.
- Enforce budgets and store every round.
- Acceptance: the loop improves a measurable finding without breaking the technical gates.

### Phase 4: examples and knowledge base

- Curate a local set of own or compatible projects and instrument presets.
- Add retrieval only if the curated set outgrows simple lookup.
- No vector database until the local set and the queries justify it.

### Phase 5: service and sharing

- Optional Axum API, job queue or MCP tools, only if another client needs them.
- Persist compositions and reports in the existing SQLite database or a sibling table.

## Alternatives considered

- **A separate `nes-composer` crate or service with Rig, Tokio, Axum, Qdrant, Swiftide and MCP.** Rejected for phase 1: it duplicates the LLM client, the score, the history and the single binary before the musical loop is proven. The typed tools can move to a separate crate later without a rewrite.
- **`audio8bit` as a dependency.** Rejected: PolyForm Noncommercial, and its output is a monophonic lead with a bass-heavy mix. Its ideas (stems, transcription, arpeggios, echo) are already reimplemented.
- **`chipcore` only.** Kept as a fallback and a test oracle, not as the primary renderer: no editable project, no NSF/ROM, thinner instrument model.
- **A prompt-only composer.** Rejected: hardware rules in prose are not enforceable. The model and the validator are the contract.

## Open questions

- Should covers ever join the channel pipeline and the video stage, or stay a separate tool?
- Text project or binary `.fms` as the canonical artifact? Text is diffable; binary is what FamiStudio saves.
- How deep should musical evaluation go? Chroma and onsets are cheap; note-level comparison needs a transcription of the reference.
- Which LLM for compose mode: the local llama-server used for prompts, or the judge backend? The schema and validation matter more than the model.
- Do we need a second hardware profile (Game Boy) before the NES one is solid?
- Where do curated examples live: repository with licenses, or a user-local library like the reference images?

## Prior art

The initial draft of this RFC (in Spanish) proposed a standalone `nes-composer` repository with Rig, Tokio, Axum, Qdrant, Swiftide, FastEmbed and an optional MCP server, plus a five-phase plan from vertical slice to service. This RFC keeps the goals, the typed-model principle, the deterministic tools and the licensing rules, and drops the separate stack for phase 1 in favor of the existing binary. The cover prototype and the FamiStudio experiments are the evidence behind the first phase.
